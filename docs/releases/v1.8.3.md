# v1.8.3

Fix: **scheduled scans/applies failed with "cipher too short" for multi-host and tag jobs.**

## Root cause

The scheduler resolves a job's target hosts in `resolveJobHosts`:
- single-host jobs → `db.GetHost` (selects `secret_cipher`) ✓
- multi-host jobs → `db.ListHostsByIDs`
- tag jobs → `db.ListHostsByTag`

But `ListHostsByIDs` and `ListHostsByTag` are thin filters over `ListHosts`, which **deliberately
omits `secret_cipher`** so the API never leaks SSH credentials to the dashboard. So the scheduler
handed the SSH client hosts with an **empty encrypted secret**, and decryption failed immediately
with `cipher too short` — for *every* host in the job. Single-host scheduled jobs worked; multi-host
and tag jobs never did. (Manual/interactive scans were unaffected — they load each host via `GetHost`.)

## Fix

`resolveJobHosts` now re-loads each tag/multi-host target via `GetHost` so it carries its encrypted
SSH secret before the scan/apply runs. The list helpers stay secret-stripped (safe-by-default for
any future API caller); the scheduler re-hydrates explicitly.

## Companion fix — `ListHosts` connection-pool deadlock

While adding the regression test, it surfaced a latent bug: `ListHosts` called
`GetHostNotificationPrefs` (a query) *inside its open `rows` loop*. That nested query needs a
second DB connection; under a constrained pool it deadlocks waiting on the connection the cursor
holds. Production's default pool masked it, but it would hang under connection pressure (and hung
the test's single-connection DB outright). Fixed by buffering the rows, closing the cursor, then
fetching prefs — the correct Go SQL pattern.

## Tests
- `db/jobs_test.go::TestSecretCipherLoadingContract` — locks the contract: `GetHost` loads
  `secret_cipher`, `ListHostsByIDs` strips it. Guards against a regression that would re-break
  scheduled scans (and exercises `ListHosts`, which would otherwise have kept the deadlock hidden).

## Notes
- No DB or config change. After deploying, your existing multi-host/tag scan & apply schedules
  will run correctly.
