# v1.8.6

UX: **explain when a restarted service stays flagged by needrestart** (the containerd case)
instead of leaving it looking like the restart "did nothing."

## Background

needrestart commonly flags `containerd.service` after a package upgrade and keeps flagging it
even after a `systemctl restart containerd` — whether done by Patchdeck or by hand. The daemon
restarts fine, but each running container has a long-lived `containerd-shim` process that keeps
the *old* binary mapped, and a service restart doesn't recycle those. (Confirmed against a real
host: the restarted daemon maps current libs; the shim processes still map the deleted
`/usr/bin/containerd-shim-runc-v2`.) Only recycling the containers or rebooting clears it.

Previously the restart appeared to do nothing — the service restarted, but the card still
showed it flagged, with no explanation.

## Change (frontend only)

In the host details, when a service the user just restarted is **still flagged** once the
follow-up scan settles, Patchdeck now shows an amber note:

> *Still flagged after restart: `containerd.service` — the service was restarted, but needrestart
> still flags it. This is expected for units like containerd: each running container keeps a
> long-lived shim process mapping the old binary… Recycle the affected containers, or reboot the
> host to fully clear it.*

…with a **"Reboot host to clear"** button that routes to the existing reboot flow (with recovery
monitoring). The note is detection-based (any restarted unit that doesn't clear), gated on no
action in flight so it only appears after the re-scan refreshes the status.

We deliberately did **not** add an auto "restart Docker" action: it restarts every container on
the host (full service outage), can silently no-op under Docker `live-restore`, and would kill
Patchdeck itself on a host where it runs in Docker. Reboot is the reliable, already-handled
remedy.
