# v1.8.4

Fix: **scheduled jobs now run in your timezone** (the `TZ` env var is finally respected).

## What was wrong

Two issues stacked:
1. The scheduler evaluated cron expressions against **`time.Now().UTC()`** — hardcoded UTC — so
   `0 3 * * *` fired at 03:00 UTC regardless of `TZ`.
2. The minimal Alpine runtime image (since v1.8.0) ships **no `tzdata`**, so even with the code
   using local time, Go couldn't resolve `TZ=America/...` and would fall back to UTC.

## Fix

- **Cron is now evaluated in local time** (`time.Now()`), so schedules fire in the container's
  timezone. The displayed "next run" (`NextRun`) is computed in the same zone, and the per-minute
  dedup keys normalize to UTC internally so they stay correct across zones.
- **The IANA timezone database is embedded in the binary** (`import _ "time/tzdata"`), so
  `TZ=<zone>` resolves on the minimal image with no extra package (~450 KB, no image bloat).
- Startup now logs the active timezone, e.g.
  `scheduler timezone: PDT (local now 2026-06-15 21:40:11 -0700) — set the TZ env var to change`,
  so you can confirm it took effect.

## Usage

Set `TZ` on the container (IANA name), e.g. in compose:
```yaml
environment:
  TZ: America/Los_Angeles
```
Restart the container; cron schedules now fire in that zone. Confirm via the startup log line above.

## Tests
- `scheduler/scheduler_test.go::TestNextRunRespectsTimezone` — a daily `0 3 * * *` fires at 03:00
  in the evaluation timezone (UTC+5 in the test), not 03:00 UTC.

## Notes
- No DB or config-schema change. Activity-log timestamps remain stored in UTC (display only).
