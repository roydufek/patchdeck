# v1.8.7

Security: **rebuild to pick up Go 1.25.12**, clearing a fixable HIGH in the Go standard
library that was compiled into the shipped binary.

## Background

A scheduled security audit (trivy + grype + govulncheck + npm audit) found that the running
image — built roughly four weeks earlier — carried **CVE-2026-39822** (HIGH, fixable):

> `os`: Go `os.Root` symlink-following vulnerability allows directory traversal

The finding is in the **Go standard library linked into the binary**, not in Patchdeck's own
code or in any third-party dependency. The image had been built with `go1.25.11`; the fix
landed in `go1.25.12`.

Because the Dockerfile's builder stage tracks the floating `golang:1.25-alpine` tag, simply
rebuilding picks up the patched toolchain — **no source change was required** beyond the
version bump in this release.

## Change

- `AppVersion` 1.8.6 → 1.8.7. No functional, API, DB, or config change.
- The release exists to produce a **freshly built image** so prod stops running a binary with
  a known-fixable HIGH.

## Notes

- **The two scanners disagreed, again.** trivy rated the stdlib issue **HIGH**
  (`CVE-2026-39822`) while grype rated the same issue **Medium** (`GO-2026-5856`), so
  `grype --only-fixed --fail-on high` passed while trivy's gate failed. Only the two-scanner
  gate caught it. (Same lesson as v1.8.0, where trivy caught a `libcrypto3` CVE grype missed.)
- **This class of finding is invisible to source-level tooling.** `govulncheck` reports
  reachability in *source*, and `npm audit` covers only the frontend; neither sees the Go
  toolchain a binary was compiled with. Only an image scan catches a stale stdlib — which is
  why periodically re-scanning an already-green image matters, even with no code change.
- `busybox`/`busybox-binsh`/`ssl_client` still carry `CVE-2025-60876` (Medium, **unfixed
  upstream**). Not actionable and correctly excluded by the fixable-only gates; `apk upgrade`
  will collect the fix when Alpine ships one.
