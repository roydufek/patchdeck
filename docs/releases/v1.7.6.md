# v1.7.6

Two reliability/UX fixes driven by real fleet behavior (rebooting hosts + mid-apply disconnects).

## Per-host connectivity — status dots resolve independently

**Problem:** the dashboard fetched all host statuses from a single `GET /api/hosts/connectivity`
that probed every host concurrently but only returned **one** response after the *slowest*
host finished. A host that was rebooting burned the full connectivity timeout (default 15s),
so **every** status dot stayed frozen until that one host timed out.

**Fix:** connectivity is now checked **per host**.

- New endpoint `GET /api/hosts/{id}/connectivity` returns one host's reachability + uptime.
  Shared `probeConnectivity` helper backs both it and the (retained) bulk endpoint.
- The dashboard fires one independent React-Query (`useQueries`, key `['connectivity', id]`)
  per host. Each dot flips the moment *its own* check returns; a slow/rebooting host shows
  "checking…" for its own timeout without holding any other host hostage.

## Apply: verify-after on a mid-apply SSH disconnect (no more false "FAILED")

**Problem:** `apt-get -y dist-upgrade` runs over a single SSH exec. If a package post-install
restarts sshd/networking, or the host reboots on a kernel update mid-apply, the connection
dropped and Patchdeck reported the apply as **FAILED** (and sent a failure notification) — even
though dpkg had almost certainly completed on the host. A false alarm.

**Fix:** classify a mid-apply connection drop as *interrupted*, not *failed*, and verify.

- `sshx`: a new `ErrConnectionLost` sentinel marks errors where the SSH channel dropped
  (`*ssh.ExitMissingError`, EOF, reset, "remote command exited without …") as opposed to the
  remote command exiting non-zero (a genuine failure — `*ssh.ExitError` is explicitly NOT
  treated as a connection loss). Privilege-escalation fallbacks no longer re-run the command
  after a connection loss. `ApplyUpdates`/`ApplyUpdatesStreaming` return a typed
  `ApplyInterruptedError` (with `ChangedSoFar`) on that signal.
- Interactive apply (`/apply/stream`): emits a new SSE `interrupted` event instead of `error`,
  records an `apply_interrupted` activity entry, and sends **no** failure notification. The UI
  shows "Connection lost during apply — verifying…", starts the recovery monitor, and re-scans
  once the host is back to reflect real state.
- Scheduler: a scheduled apply that disconnects is logged as `apply_interrupted` (no FAILED
  alert) and reconciled by the next scheduled scan.
