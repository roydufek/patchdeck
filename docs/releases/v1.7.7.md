# v1.7.7

Service-restart fixes — driven by "privilege escalation failed" errors when restarting
`systemd-logind.service` / the systemd manager on prod.

## Root cause: a misleading error masked the real failure

`RestartServices` ran `systemctl restart <units>` through `runPrivileged`, which tries
`sudo -n` → `sudo -S` → `su` and only reports failure if **all three** fail. It could not
distinguish **"sudo was rejected"** from **"sudo worked but the command exited non-zero."**
So when `systemctl restart` genuinely failed for a unit, escalation *succeeded* all three
times, the real `systemctl` error was discarded, the command was needlessly re-run under
every method, and the operator saw the generic **"privilege escalation failed: sudo -n,
sudo -S, and su fallback all failed"** — hiding the actual reason. (The streaming path used
by scan/apply already avoided this by probing `sudo -n true` first.)

## Fixes

- **Probe-then-commit escalation** (`runPrivileged`, and the password/su fallbacks in
  `runPrivilegedStreaming`): each method is probed with a no-op (`true`); on success we
  commit to it and return the **real command's** result. A command that legitimately exits
  non-zero now surfaces its own error (e.g. the actual `systemctl` message) instead of being
  masked — and is no longer re-run under every fallback. This also improves scheduled-apply
  error messages (the scheduler uses the non-streaming `ApplyUpdates`).
- **Per-service restart**: `RestartServices` now restarts each selected unit independently
  and aggregates results, so one failing/refused unit (e.g. `systemd-logind.service`) is
  isolated and reported with its real error rather than failing the whole batch opaquely.
  The error message lists exactly which units failed and why; successes still apply.
- **systemd manager → `daemon-reexec`**: a needrestart entry that is really the manager
  (PID 1 — `systemd`, `systemd-manager`, `init`, …) can't be `systemctl restart`ed as a
  unit; it's now mapped to `systemctl daemon-reexec` (the correct action) instead of a
  guaranteed failure.
- **Connection drop during restart = likely-success**: restarting a session/network-critical
  unit that drops the SSH connection (`ErrConnectionLost`, from v1.7.6) is reported as
  "connection dropped during restart (likely restarted; reconnect to confirm)" rather than a
  hard failure.

## Tests
- `sshx/connection_lost_test.go` — `isSystemdManagerUnit` truth table (manager names →
  daemon-reexec; logind/journald/dbus/etc. → normal restart).

## Notes
- No DB schema change. No config change.
- Behavior change: a partial restart failure now returns the real per-unit reasons (HTTP 500
  with detail) instead of a single opaque escalation error.
