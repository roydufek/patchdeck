# v1.8.5

Fix: **the 30 s rate limiter was blocking legitimate chained actions** — bulk apply showed
"rate limited" on every host, and a service restart right after an apply silently failed.

## Root cause

The per-host limiter used a single 30 s window shared across **all** SSH operations
(`Allow(hostID)` for scan, apply, restart, power). So back-to-back actions on the same host
collided:
- **Bulk apply** runs `apply` then immediately `scan` on each host (to refresh status). The
  scan hit the window the apply had just consumed → **429 "rate limited"** on every card,
  even though the apply itself succeeded.
- **Restart after apply** (e.g. apply-all, then restart containerd) → the restart hit the
  apply's window → 429. That error renders on the collapsed card, not the expanded host
  details, so it looked like "nothing happened, no error."

## Fix

The limiter is now **per-host *and* per-operation** (`hostID:scan`, `hostID:apply`,
`hostID:restart`, `hostID:power`). Different actions no longer block each other — apply, its
follow-up scan, and a restart can run back-to-back — while a rapid repeat of the *same*
action on the *same* host is still debounced (abuse protection preserved).

## Tests
- `ratelimit/limiter_test.go::TestHostLimiterPerOperation` — same-op repeat is blocked;
  different ops on the same host and other hosts are independent; the op unblocks after the
  cooldown.

## Note on containerd / needrestart

Separately: restarting `containerd.service` may not clear needrestart's flag if containers
are running — `containerd-shim` processes survive a containerd restart and can keep older
libraries mapped, so needrestart keeps flagging it until the containers are recycled or the
host is rebooted. That's a containerd/needrestart behavior, not a Patchdeck bug. With this
release the restart will actually run (no longer silently rate-limited) and report its result;
if it still shows as needed afterward, recycle the containers or reboot to fully clear it.

No DB or config-schema change.
