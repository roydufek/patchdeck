# v1.8.13

Fix: **bulk reboot now monitors every host coming back, with live progress** — instead of
watching only one and abandoning the rest.

## The bug

The recovery monitor was single-host by design: it tracked one `hostId`, and `startMonitor()`
tore down whatever it was previously watching. A bulk reboot loops `onReboot()` over the
selected hosts, and each call fired `startMonitor()` — so every host **cancelled the previous
host's monitor**. Only the *last* host in the loop ended up watched; it did its one post-reboot
scan, and every other host got its reboot command sent and then nothing — no wait-for-recovery,
no reconnect, no scan.

## Change (frontend only)

- **`useRecoveryMonitor` is now multi-host** — it holds a `Map<hostId, {status, attempts,
  elapsed}>` and one `/await-recovery` reconnect loop *per host*. `startMonitor(hostId, …)`
  adds a monitor without disturbing the others (it only replaces that host's own prior one).
  The server endpoint is already per-host, so this is purely client-side; no backend change.
- **Per-host recovery banner** keys off the map, so in a bulk reboot every host shows its own
  "waiting → recovered / timed out" progress and its own post-reboot scan.
- **Live batch progress**, like bulk scan — the dashboard toolbar shows
  *"Reboots: 6/10 back · 1 timed out…"* updating as hosts return, and one summary toast when the
  batch settles: *"9/10 hosts recovered · 1 timed out."*
- **Recovery outcome handler is per-host** (a Set of acted hosts, not a single boolean), so each
  host independently records "recovered / timed out" and triggers its own single refresh scan.
- **Reboot recovery timeout 180s → 300s** — headroom for slow POST/BIOS/fsck so a healthy host
  isn't falsely marked "timed out." (Service restarts stay at 120s.)

## Notes

- No backend, DB, or config change.
- A batch watcher self-clears ~30s past the recovery cap as a safety net, so a host whose reboot
  command failed to send can't leave the progress indicator stuck.
- File-ending note: the four touched frontend files were normalized CRLF→LF (matching the repo's
  move to an LF standard); diffs are content-only.
