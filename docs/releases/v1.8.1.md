# v1.8.1

Service-restart follow-up — handle needrestart entries that aren't real restartable units.

## What this fixes

With v1.8.0 surfacing the *real* restart error, the actual problem became visible:
needrestart flags **`systemd-user`** (the per-user `systemd --user` manager) after a shared
library upgrade, but there is no `systemd-user.service` to `systemctl restart` — so the
restart failed with "Unit systemd-user.service not found." (On hosts without passwordless
sudo, the `su` password prompt also leaked into the message as a stray "Password:".)

## Changes (`sshx`)

- **`systemd-user` / `systemd-user.service` are filtered out of `needs_restart` at scan time**
  — they're the per-user service manager (refreshes on next login/reboot), not a restartable
  system unit, so they no longer appear as an actionable "needs restart" service. The real
  `user@<uid>.service` and `systemd-user-sessions.service` units are unaffected.
- **`RestartServices` skips, rather than hard-fails, on non-restartable units**: a
  `systemctl restart` that returns "Unit … not found / not loaded" is reported as *skipped*
  ("not a restartable unit on this host"), and the per-user manager is skipped up front. A
  restart of only such entries now succeeds (nothing to fail) instead of showing a red error.
- **Stray `su` "Password:" prompt text is stripped** from surfaced command errors, so
  failures on hosts that fall back to `su` (no passwordless sudo) read cleanly.
- (From v1.8.0, still in effect: per-service restart, real error surfacing, systemd manager
  → `daemon-reexec`, connection-drop = likely-restarted.)

## Tests

## Notes
- No DB or config change. After deploying, a re-scan drops `systemd-user` from the host's
  restart list automatically.
